# MySQL 자동 마이그레이션

개발 환경은 Flyway로 `src/main/resources/db/migration`의 SQL과 `db.migration` 패키지의 Java 마이그레이션을 서버 시작 시 실행한다. 적용 내역은 같은 DB의 `flyway_schema_history`에 기록한다. 기존 DB에는 버전 0을 기준점으로 기록한 후 미적용 변경을 실행한다. 비어 있는 DB는 기존 Hibernate 스키마 생성 후 마이그레이션을 실행한다.

여러 인스턴스가 동시에 시작해도 한 인스턴스만 스키마 초기화와 마이그레이션을 수행하도록 MySQL 잠금을 사용한다. Hikari 연결 풀은 잠금과 초기화에 최소 2개 연결이 필요하다. 필수 테이블 일부만 있거나 예상하지 못한 기존 테이블만 있는 DB는 자동으로 초기화하지 않고 시작을 중단한다. DB 접속 계정에는 스키마 조회·생성·변경과 인덱스·외래키 생성, 마이그레이션 이력 및 초기 데이터 쓰기 권한이 필요하다.

## 기능별 변경

- 문의·회원·채팅·금칙어·버전·도움말·공지·뉴스·약관 마이그레이션은 `AdminFeatureMigrations`에 준비돼 있다. 각 기능의 대표 클래스가 배포된 경우에만 해당 마이그레이션을 등록하므로, 아직 없는 기능의 스키마를 미리 바꾸지 않는다.
- 기간별 회원 정지는 `users.ban_expires_at`과 제재 이력의 `duration`을 자동 추가한다. 종료 시각은 UTC로 저장하며 기존 무기한 정지는 유지한다.
- 이후 기능은 자신의 PR에 버전이 유일한 Flyway 마이그레이션을 추가한다. 독립적인 기능은 서로 다른 순서로 배포될 수 있어 `out-of-order`를 허용한다. 의존 관계가 있는 뉴스 티커는 공지 테이블 생성 후 적용해야 한다.
- 기존 DB에서 수동 또는 Hibernate로 이미 생성된 컬럼과 테이블은 확인 후 유지한다. 필요한 인덱스와 외래키가 없으면 추가하고, 이름이나 삭제 규칙이 충돌하면 시작을 중단한다. 기존 데이터를 지우거나 초기 잠금 행을 덮어쓰지 않는다.
- 적용한 마이그레이션은 수정하거나 삭제하지 않고 새 버전을 추가한다. Java 마이그레이션은 SQL 파일처럼 Flyway가 자동 체크섬을 계산하지 않으므로 특히 변경하지 않아야 한다.
- 기존 `database/migrations`의 SQL은 수동 적용 이력과 검토용으로 남는다. Flyway 마이그레이션이 포함된 버전에서는 같은 SQL을 다시 일괄 실행하지 않는다.
- 기존 `V20260915__preserve_chat_messages_when_user_is_deleted.sql`도 자동 적용 대상이다. 기존 채팅 외래키가 이미 `SET NULL`이면 유지하고, 이전 삭제 규칙이면 한 번의 MySQL `ALTER TABLE`로 변경한다. 예상하지 못한 타입·참조는 수정하지 않고 시작을 중단한다.

현재 `ddl-auto: update`는 기존 기능의 스키마 초기화를 위해 유지한다. 따라서 빈 DB를 기존 애플리케이션 전체의 재현 가능한 기준 스키마로 만드는 작업까지 끝난 것은 아니다. 자동 적용 대상과 실제 DB 상태를 배포 전에 확인해야 한다.

## 실패 시

MySQL DDL은 하나의 트랜잭션으로 롤백되지 않을 수 있다. 실패하면 서버 시작을 중단한다. DB 백업과 실제 스키마·Flyway 이력을 확인하고 원인을 수정한 다음에만 Flyway 복구 절차를 수행한다. 실패 기록을 자동 삭제하거나 `repair`를 자동 실행하지 않는다. 코드 롤백 시 이전 버전에 없는 마이그레이션 이력이 있을 수 있으므로, 스키마와 이력을 먼저 확인한다.

## 검증

로컬 전용 MySQL 8 테스트는 `127.0.0.1:13308`의 비밀번호 없는 일회용 인스턴스에서만 실행한다. 테스트는 전용 임시 데이터베이스만 생성·삭제한다.

```powershell
$env:ADMIN_MIGRATION_DISPOSABLE_MYSQL = 'true'
.\gradlew.bat test --tests 'com.scorenow.migrationtest.DatabaseMigrationMySqlTest'
```
